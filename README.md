# unity-hackathon

Игра на Unity для хакатона. Начальная сцена URP используется для базовой
проверки окружения; концепция игры и окончательные целевые платформы ещё не выбраны.

## Окружение разработки

- Unity Editor **6000.6.7f1** на каждой машине для разработки и сборки.
- URP **17.6.0** и Unity Test Framework **1.8.0**.
- Git и Git LFS; Python 3.9+ для скриптов проверки репозитория и запуска тестов.
- В Unity Hub открывайте корень репозитория: в нём находятся `Assets`, `Packages`
  и `ProjectSettings`. Для просмотра стартовой сцены откройте
  `Assets/Scenes/SampleScene.unity`.
- Включены сериализация `Force Text` и режим `Visible Meta Files`.
- Добавляйте в Git `Assets` вместе с `.meta`, `Packages` вместе с файлом фиксации
  зависимостей и `ProjectSettings`. Не добавляйте `Library` и отчёты тестов.

## Первый запуск для нового участника (macOS / Fedora)

Выполняйте шаги по порядку. При ошибке остановитесь на текущем шаге и сохраните
текст ошибки. Команды ниже рассчитаны на терминал macOS или Linux.

### 1. Получите доступ и подготовьте инструменты

- Примите приглашение в приватный репозиторий
  [kaysuk/unity-hackathon](https://github.com/kaysuk/unity-hackathon) и убедитесь,
  что он открывается под вашим аккаунтом.
- Установите Git, [Git LFS](https://git-lfs.com/), Python **3.9 или новее**
  и [Unity Hub](https://unity.com/download).
- В Unity Hub войдите в свой аккаунт и настройте подходящую лицензию Unity.
  Установите Editor **6000.6.7f1**; для Mac с M1/M5 выбирайте вариант Apple silicon.
  Если версии нет в списке Hub, используйте [архив редакторов](https://unity.com/releases/editor/archive).
- Для первого открытия и тестов в редакторе модули Windows/Android/Dedicated Server
  не требуются. Их согласуем отдельно после выбора целей сборки.

Проверьте инструменты в терминале:

```sh
git --version
git lfs version
python3 --version
git lfs install
```

Ожидаются версии установленных инструментов и сообщение `Git LFS initialized.`.
`git lfs install` настраивает уже установленное расширение для пользователя,
а не скачивает его. Инструкция установки:
[GitHub Docs](https://docs.github.com/en/repositories/working-with-files/managing-large-files/installing-git-large-file-storage).

### 2. Клонируйте проект и проверьте файлы

Откройте терминал в каталоге, где хотите хранить проекты. Команда создаст
в нём папку `unity-hackathon`; не запускайте её внутри уже существующего checkout.

```sh
git clone --branch main https://github.com/kaysuk/unity-hackathon.git
cd unity-hackathon
git lfs pull
git lfs fsck
python3 scripts/check_repository.py
git status --short --branch
git log -1 --oneline
```

Для HTTPS должен быть настроен вход в GitHub через credential manager или другой
поддерживаемый способ. Пароль аккаунта GitHub для Git по HTTPS не подходит.
Если у вас уже настроен SSH, можно использовать адрес
`git@github.com:kaysuk/unity-hackathon.git` вместо HTTPS. Не вставляйте токены
в URL клонирования и не присылайте их в командный чат.

Ожидаемый результат:

- `git lfs pull` и `git lfs fsck` завершаются без ошибок;
- скрипт пишет `Repository checks passed. Unity/gameplay tests have not run.`;
- статус — `## main...origin/main`, без строк изменённых или новых файлов;
- последний коммит соответствует текущему `main` на GitHub. Запишите его SHA
  для сообщения о проверке; он будет меняться по мере разработки.

Для первого получения проекта используйте Git clone, а не Download ZIP:
нам нужны история, ветки и работа с LFS. Если копия уже существует, не клонируйте
поверх неё. Сохраните работу и закройте Unity, проверьте `git status`, затем
при чистом рабочем дереве обновите её через `git switch main` и `git pull --ff-only`.
При локальных изменениях или отказе обновления не применяйте принудительный сброс.

### 3. Откройте проект нужным редактором

Проверьте закреплённую версию до первого открытия:

```sh
cat ProjectSettings/ProjectVersion.txt
```

Ожидается:

```text
m_EditorVersion: 6000.6.7f1
m_EditorVersionWithRevision: 6000.6.7f1 (b22767f04f04)
```

В Unity Hub на вкладке Projects добавьте существующий проект с диска, выбрав
папку `unity-hackathon`, а не `Assets`. Назначьте ему Editor **6000.6.7f1**.
Не создавайте новый проект поверх клона и не соглашайтесь на обновление другой
версией редактора. Надпись «Unity 6.6» без полного номера недостаточна.

Дождитесь импорта ресурсов и установки пакетов. При первом открытии нужен доступ
к сервисам Unity и реестру пакетов. Пакеты определены файлами `Packages/manifest.json`
и `Packages/packages-lock.json`; не обновляйте их вручную ради первого запуска.

Откройте `Assets/Scenes/SampleScene.unity`, нажмите Play и затем остановите его.
Ожидается стартовая сцена шаблона URP без красных ошибок в Console.
Отсутствие игровой механики на этом этапе нормально.

### 4. Выполните тесты и проверьте состояние Git

Для первого знакомства используйте **Window > General > Test Runner**:

1. Во вкладке **EditMode** выполните **Run All** — ожидаются **4 Passed**.
2. Во вкладке **PlayMode** выполните **Run All** — ожидается **1 Passed**.

Ноль найденных тестов не означает успех. При ошибке сохраните имя теста и сообщение
из Test Runner/Console. Для получения XML и логов используйте пакетный запуск
из раздела «Unity-тесты» ниже; GUI и пакетный запуск не выполняйте одновременно.

После тестов и закрытия редактора выполните:

```sh
git status --short --branch
```

Ожидается чистое рабочее дерево. Если изменились `ProjectSettings`, `Packages`
или ресурсы, сначала посмотрите `git diff` и обсудите причину; не коммитьте
автоматически результат первого открытия и не удаляйте свои изменения вслепую.

### 5. Сообщите результат команде

Скопируйте и заполните короткий отчёт:

```text
Машина и ОС: Mac M1 Pro / Mac M5 / Fedora, версия ОС
Unity: полная версия
Ветка и коммит: main, SHA из git log -1 --oneline
LFS и repository checks: прошли / ошибка
Стартовая сцена: открывается, Play без ошибок / ошибка
EditMode: 4/4 / фактический результат
PlayMode: 1/1 / фактический результат
Способ запуска тестов: Test Runner / прямой запуск / Python
Рабочее дерево после проверки: чистое / список изменений
При ошибке: шаг, точное сообщение, соответствующий лог или XML
```

Доступ DevOps к вашему компьютеру для этого не требуется. Пока результат
не получен, работоспособность окружения на этой машине считается неподтверждённой.

## Проверки репозитория

Скрипт проверяет отслеживаемые файлы через `git ls-files`. После чистого клонирования
ничего добавлять в индекс не нужно. При разработке новые файлы, предназначенные
для коммита, сначала добавьте через `git add`, затем выполните из корня репозитория:

```sh
python3 scripts/check_repository.py
git lfs fsck
```

GitHub Actions выполняет эти проверки для pull request в `main` и при push в `main`.
Зелёный статус этого workflow не подтверждает прохождение Unity-тестов или сборку игры.

## Unity-тесты

Перед запуском тестов в пакетном режиме сохраните работу и закройте редактор Unity
с этим проектом. Не запускайте два процесса Unity на одном checkout.

Python-обёртка доступна, но её полный реальный прогон ещё не подтверждён
(см. ограничения ниже). Команда для её проверки:

```sh
python3 scripts/run_unity_tests.py
```

Скрипт ищет редактор закреплённой версии в стандартных каталогах Unity Hub
на Linux, macOS и Windows. Если редактор установлен в другом месте:

```sh
python3 scripts/run_unity_tests.py --editor /absolute/path/to/Unity
```

Для запуска одной группы используйте `--platform EditMode` или `--platform PlayMode`.
По умолчанию графическое устройство отключено. Параметр `--graphics` включает его
на машине с работающим графическим окружением. Успешный запуск без графики
не подтверждает правильность рендеринга, сенсорного ввода или производительность
на целевых устройствах.

- **EditMode:** версия редактора, включённые сцены сборки, настройки сериализации
  для работы с Git и назначение URP для активного уровня качества.
- **PlayMode:** загрузка первой сцены сборки, наличие активной камеры,
  отсутствие потерянных скриптов и неожиданных ошибок.
- Результаты: `TestResults/EditMode.xml`, `TestResults/PlayMode.xml` и логи.
- Ненулевой код завершения редактора, отсутствие XML, провал тестов или отсутствие
  успешно выполненных тестов приводят к ошибке команды. Старый XML удаляется
  перед каждым запуском соответствующей группы.

### Результаты проверки и ограничение скрипта запуска

На Fedora с Unity 6000.6.7f1 при прямом запуске редактора без графики успешно
прошли четыре EditMode-теста и один PlayMode-тест. Проверки собранных приложений
на целевых платформах и визуальные проверки не выполнялись. При запуске из среды агента
Unity дочерним процессом Python завершалась сигналом `SIGKILL` до выполнения тестов.
Причина не установлена; проблема не доказана как специфичная для Fedora, лицензии
или ограничений среды. Поэтому полный цикл запуска через Python в этой среде
**не подтверждён**. Логика проверки результатов скрипта проверена на успешных,
проваленных, пустых, повреждённых, отсутствующих и устаревших отчётах,
а также при ненулевом коде завершения редактора.

### Прямой запуск с сохранением свежих отчётов

Этот способ прошёл проверку на Fedora. На Mac он пока требует проверки участником.
Сначала закройте редактор. В терминале из корня репозитория задайте путь к Unity
**одной** подходящей командой:

```sh
# macOS, стандартная установка через Unity Hub:
unity_editor="/Applications/Unity/Hub/Editor/6000.6.7f1/Unity.app/Contents/MacOS/Unity"
```

```sh
# Fedora, стандартная установка через Unity Hub:
unity_editor="$HOME/Unity/Hub/Editor/6000.6.7f1/Editor/Unity"
```

При нестандартной установке укажите свой абсолютный путь. Затем в том же терминале
выполните блок целиком. Он запускает группы последовательно, создаёт новый каталог
для каждой пары отчётов и останавливается при ошибке. Скобки ограничивают `exit`
этим блоком и не закрывают ваш терминал.

```sh
(
  test -x "$unity_editor" || { echo "Не найден исполняемый файл Unity"; exit 1; }
  mkdir -p TestResults || exit 1
  test_run_dir=$(mktemp -d "$PWD/TestResults/run-XXXXXXXX") || exit 1
  printf 'Каталог отчётов: %s\n' "$test_run_dir"

  for platform in EditMode PlayMode; do
    "$unity_editor" \
      -batchmode -nographics -projectPath "$PWD" \
      -runTests -testPlatform "$platform" \
      -testResults "$test_run_dir/$platform.xml" \
      -logFile "$test_run_dir/$platform.log"
    unity_exit=$?
    printf '%s: код завершения Unity = %s\n' "$platform" "$unity_exit"
    test "$unity_exit" -eq 0 || exit "$unity_exit"

    python3 - "$test_run_dir/$platform.xml" <<'PYXML'
import sys
import xml.etree.ElementTree as ET

root = ET.parse(sys.argv[1]).getroot()
cases = root.findall(".//test-case")
passed = sum(case.get("result") == "Passed" for case in cases)
failed = sum(case.get("result") == "Failed" for case in cases)
print(f"{sys.argv[1]}: result={root.get('result')}, "
      f"passed={passed}, failed={failed}, total={len(cases)}")
if root.get("result") != "Passed" or not cases or passed != len(cases):
    sys.exit("Ошибка: не все найденные тесты прошли")
PYXML
    report_exit=$?
    test "$report_exit" -eq 0 || exit "$report_exit"
  done
)
```

Ожидаются код Unity `0` для каждой группы, `result=Passed`, EditMode —
`passed=4, failed=0, total=4`, PlayMode — `passed=1, failed=0, total=1`.
Число тестов относится к текущему набору и изменится при добавлении новых тестов.
В напечатанном каталоге останутся оба XML и оба лога. Старые отчёты не удаляются;
в Git содержимое `TestResults` не добавляем.

Не добавляйте `-quit`: Test Framework завершает процесс после записи результатов.
Прямой запуск не имеет внешнего тайм-аута. Если он не завершился за 15 минут,
посмотрите соответствующий `.log` из другого терминала и сообщите о зависании.
При необходимости прервите запуск через Ctrl+C; перед повтором убедитесь,
что процесс завершился. Не запускайте вторую копию параллельно.

В этой среде также наблюдалось зависание при загрузке закэшированных сборок.
Перенос `Library/ScriptAssemblies` в игнорируемую резервную папку внутри `artifacts/`
при закрытом Unity вызывал повторную компиляцию и позволял завершить прямые запуски.
Исходный `Library` и последующие резервные копии кэша сборок сохранены локально
в `artifacts/`. Это восстанавливаемые кэши, а не исходники проекта.
Причина проблемы не установлена.

Это базовые проверки работоспособности проекта, а не тесты геймплея или мультиплеера.
Unity-тесты пока запускаются локально. Workflow GitHub выполняет только проверки
репозитория; для автоматического запуска Unity-тестов предстоит настроить runner
с редактором Unity и действующей лицензией.

## Планируемые целевые сборки

Windows x64 (первоначально Mono), Android ARM64 (IL2CPP) и Linux x86-64
Dedicated Server. Установка модулей сборки, настройка профилей, автоматизация
и проверки на устройствах — отдельные этапы. Наличие платформ в этом списке
не означает, что сборки для них уже готовы.

## Если первый запуск не удался

| Симптом | Что проверить и передать команде |
| --- | --- |
| `Repository not found` или ошибка авторизации | Принято ли приглашение, под каким аккаунтом настроен Git, открывается ли репозиторий в браузере. Не присылайте токены. |
| Git не знает команду `lfs` | Установите Git LFS, затем выполните `git lfs install` и повторите `git lfs pull`. |
| Ошибка загрузки LFS или пакетов | Сохраните точную ошибку; проверьте доступ к GitHub или реестру Unity соответственно. Не заменяйте отсутствующие ресурсы пустыми файлами. |
| Hub предлагает другую версию | Установите и выберите `6000.6.7f1`, не обновляйте проект без согласования. |
| Ошибка лицензии | Проверьте вход и лицензию в Hub; если не помогло, передайте текст ошибки. |
| Проект уже открыт | Сохраните работу и закройте редактор этого проекта перед пакетными тестами. |
| Нет тестов, XML отсутствует или тест красный | Это не успех: передайте способ запуска, SHA, код завершения и лог/сообщение теста. |
| `SIGKILL`, зависание или неожиданное изменение файлов | Сохраните лог и `git status`. Не удаляйте `Library`, кэши или изменения автоматически; сначала разберём причину. |

## Что подтверждено и что ещё предстоит

- **Подтверждено на Fedora:** прямые запуски EditMode (4/4) и PlayMode (1/1)
  с Unity 6000.6.7f1 без графики. Повторный прогон на `main` дал оба отчёта.
- **Пока не подтверждено:** первое клонирование и тесты на Mac M1 Pro/M5,
  полный реальный прогон через Python-обёртку.
- **Ещё не настроено:** Unity-тесты и сборки в CI, публикация сборок, сетевой стенд,
  сервер и деплой. Защиту ветки с обязательными проверками нужно проверить отдельно.
- **Ограничения:** тест версии сравнивает Editor с текущим `ProjectVersion.txt`,
  который другой редактор может переписать; это не защита от обновления Unity.
  Проверяется URP активного качества, а не всех уровней. Smoke-тесты не проверяют
  геймплей, мультиплеер, FPS, визуальное качество или готовые приложения на устройствах.
